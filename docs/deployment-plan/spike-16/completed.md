# Spike 16 — Completed

## S16-16 — Kinship answers are composed from the pivots, and the Family read is one pass

**Landed 2026-11-13** in [#814](https://github.com/mendahu/provenencia/pull/814). Nothing a researcher sees changes. A person's implied links and siblings are composed from the cached kinship pivots at each read, so a commit no longer empties two catalog-wide caches: only the pivots one hop from what it touched are recomputed. The Family section reads each person's kin in one batched `Relationships` call and the `LoadRelationships` and `LoadSiblings` loaders are gone; `edgeKey` length-prefixes its parts. A warm Promote proposal costs more (1.56–1.74× the base at 4,000 persons and 1.68–2.27× at 16,000, run to run on a loaded M1; the ship log has the tables), and the proposal after a commit is unchanged within noise. The user accepted the warm cost: `budgetWarm` is 950 ms and memoising `For` is parked in `docs/ideas/promote-ranking.md`.

## S16-30 — Provenance records compose from cached records

**Landed 2026-11-13** in [#812](https://github.com/mendahu/provenencia/pull/812). A Conclusion page's provenance record is the node's outcome row, the Observation and Subject from the graph's cached records, and the Source record, composed with no SQL: the records now carry each Observation's Citation label, page, Artifact and uncertainty and index Observations by id (each Citation's locator is parsed once per graph load, and its Observations share the words), so a Citation edit reaches the sheet through the existing graph drop. `sqlRecords`, `sqlToponyms`, `loadRecords`, `toponymsOf` and the detail read's date and name lookups are gone, a Person's life rows compose only the Property each owner is read for, and the detail handler reads the subject type from the graph vocabulary. A warm open reads nothing from SQL but the pictures' paths. The records take 22.4 MB at 4,096 held graphs (17.2 MB before). No change a researcher can see, so no version bump.

## S16-20 — One match index that Apply keeps current

**Landed 2026-11-13** in [#827](https://github.com/mendahu/provenencia/pull/827). The match index is one registry entry with a Build: the profile of every unmerged person, event and place and the shortlist postings filed from them, built at open by `promotealign.Warm`. A commit no longer drops it: its Apply re-profiles the commit's roots and the people at root events, drops the handles that left, and refiles only the handles whose profile changed (`shortlist.Index.Put` and `Remove`), then empties the candidates only when something changed. The entry takes 34.0 MB at 4,000 persons and 55.1 MB at 16,000; a proposal after a handle commit takes 391 ms and 667 ms against 558 ms and 920 ms. No change a researcher can see, so no version bump.
