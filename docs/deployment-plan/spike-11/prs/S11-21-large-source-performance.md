## 1. Objective

A Source with 100 Subjects proposes without a noticeable wait, re-proposes after a row decision at once, and a page of births at a big city no longer freezes Promote. A budgeted Go test on a realistic catalog holds Promote to those times in every `scripts/check-pr.sh` run, so a later change that makes Promote slow fails a test instead of a dogfood session.

**Why now.** Each layer PR since S11-13 logged a performance follow-up to this PR (map scope entry). Measured while planning with a throwaway prototype of this plan's fixture and fixes (4-core Linux, the class of CI's `ubuntu-latest`), `main` @ `c93b3fb`:

| Run | `main` | Prototype of this plan |
| --- | --- | --- |
| 100-Subject Source, cold (graph dropped) | 1.24 s | 1.3 s |
| 100-Subject Source, warm repropose | 450 ms | 105 ms |
| 100-Subject Source, first proposal after a handle commit | 650 ms | 680 ms |
| A Source of 30 births all located at one place with 6,000 filed events, cold | 18.6 s | 2.9 s |
| The same Source, warm | 16 s | 1.6 s |
| Evidence on all 58 handle rows, warm | 20 ms, 0 graph queries | same |
| Warm Evidence / Propose, raw SELECTs | 7 / 8 (5 / 6 since S12-09 removed `SoleGraph`) | 0 / 1 (`MAX(revision)` only) |

The prototype is not in the repo; the numbers are what this PR's test reproduces. Its Evidence figure was measured without the product alias tables. With them installed (D-11), every warm `Evidence` call rebuilt the alias index from the warm tables (1,235 sets, 13,341 allocations, about 1.5 ms): 90–125 ms for the pass on an Apple M1 after STEP-8, against the 100 ms budget (ship log, round 0). D-12 removes the rebuild. The prototype measured 2 / 3 raw SELECTs; the 2 were `SoleGraph`'s, which S12-09 ([#535](https://github.com/mendahu/provenencia/pull/535)) deleted, so this PR takes warm Evidence to 0 and makes the slice Check "a warm evidence open issues no catalog query" true. The one-place Source spends its time scoring every one of the city's 6,000 events for each of the 30 births, several times (S11-16 PRF-1). The warm repropose spends two thirds of its time in `graphalign.Candidates` re-running subject compare on about 61,000 shortlisted pairs (S11-15 PRF-3: a common given name keys 10% of the catalog), which no decision changes. The user set the budgets and the remedies (2026-10-24): §5 D-1 and D-2.

**What stays.** Every proposal: the same rows, bands, scores and reasons as `main` on every existing test and golden (the prototype passed `core/graphalign`, `core/database/promotealign`, `api/...` unchanged). The shortlist index and profiles still drop on every handle commit. `Propose` still reads `MAX(revision)`. No registry number changes.

## 11. Risks and stop conditions

| Risk | Mitigation |
| --- | --- |
| A budget flakes on a slow or busy CI runner | D-1's headroom is 1.7× at its tightest (one-place Source cold); cold and after-commit runs take the fastest of 2, warm runs the fastest of 3 |
| The bound drops the handle that would have won | It keeps the most similar `TopK` plus ties, the same rule shortlisted candidates already follow; every golden stays green |
| The candidates memo serves a stale list | It lives on the Source's Evidence graph memo and checks the match index generation (D-8); T-2 and T-6 compare with a dropped graph |
| The pair memo grows large | It dies with one `Align`; the prototype's heap without a cross-run memo was 52 MB on the one-place Source |
