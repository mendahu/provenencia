# Conflict brackets ignore multiple-cardinality properties

- **Date:** 2026-10-26
- **Type:** Bug (display rule)
- **Where:** Evidence graph / subject cards (cited property rows)
- **Annoyance (verbatim):** "Conflict brackets on the subject codes in the evidence graph should not show up for values with multiple cardinality."
- **Consequence:** A Property declared *multiple* (e.g. `languages_spoken`, `interests`, or any researcher Property set to "several values") paints the ochre conflict bracket, the "Conflict — competing values" legend, and the "one of N values" accessibility phrase as soon as a card carries two rows for it — even though several values is exactly what that cardinality means. Real conflicts on single-value Properties get lost in the noise, and the card suggests the researcher has something to resolve when they do not.
- **Wanted:** The bracket (and legend / a11y count) only appear for Properties whose cardinality is *single*. Multiple-cardinality rows list plainly, matching how reconciliation already treats them (`StateMultiple`, not `StateMixed`).

## How it works today (observed, not fixed)

- **The conflict check.** `macos/App/Features/EvidenceGraph/EvidenceCitedPropertyMarks.swift` — `conflictCounts(in:)` counts observations per `propertyKey` on one card; `isConflicted`, `cardHasConflict`, `conflictRuns` (the bracket runs `EvidenceCardView.swift` paints at ~L489), `graphHasConflict` (drives the legend in `EvidenceGraphView.swift` ~L319), and `accessibilityLabel(… conflictCount:)` all reduce to "same `propertyKey` appears ≥ 2 times". **Cardinality is never consulted.** Polarity is the only other input (`isNegated`), and bridges filter out the connect-sentence keys first (`extraObservations`).
- **What the check sees.** `CatalogObservation` (`macos/App/Platform/GenealogyStore.swift`) carries `propertyKey`, `propertyLabel`, `propertyValueType` — denormalised from the Go `Observation` proto (`property_key` / `property_label` / `property_value_type`, `api/proto/engine.proto`). It does **not** carry cardinality, so the marks helper has nothing to branch on without a lookup.
- **Where cardinality lives.** Go: `core/propertymeta` (`CardinalitySingle` / `CardinalityMultiple`, "empty reads as single"), stored on `properties.cardinality` (migration `000052.sql`), edited on the Properties page (`PropertiesModel`, L10n "one value" / "several values" copy). Reconciliation already honours it: `core/autoreconcile/autoreconcile.go` returns `StateMultiple` for >1 surviving values when the Property is multiple and `StateMixed` only for single. Swift: `CatalogProperty.cardinality` ("single | multiple") is on the properties snapshot.
- **Is the data reachable from the card?** Yes. `EvidenceGraphModel.fieldsSnapshot` already holds a `PropertiesSnapshot` (`QueryHandle<PropertiesSnapshot>` on `fieldsKey`), and `EvidenceGraphView` reads the same handle. So a cardinality-aware check could pass a `propertyKey → cardinality` (or `propertyID → CatalogProperty`) map into `EvidenceCitedPropertyMarks`, or the Go side could add `property_cardinality` beside `property_value_type` on the `Observation` proto so the card needs no join. Either way the rule change is confined to the helper plus its three callers.
- **Tests.** `macos/ProvenenciaTests/` has S8-06 coverage for the marks helper (search `EvidenceCitedPropertyMarks`); a "two rows of a multiple Property do not conflict" case would go there.
- **Origin.** The rule dates from S8-06 (cited property marks), which predates property cardinality (`properties.cardinality` arrived with migration `000052`; the constants moved to `core/propertymeta` in S11-22 and reconciliation honours them from S11-09). The graph marks were never revisited after cardinality landed.
