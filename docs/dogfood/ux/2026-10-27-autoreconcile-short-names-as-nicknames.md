# Auto-reconciler: emit folded short names as nicknames

- **Date:** 2026-10-27
- **Type:** Feature request (reconciliation behaviour)
- **Where:** Auto-reconciler / Person name / Conclusion detail
- **Annoyance (verbatim):** "Right now the auto reconciler will fold a given name that is a short form of a true name into its true name. I want to preserve that behavior but instead of folding it in and making it go away, I want it to be output as a nickname rather than a first name."
- **Consequence:** When sources record *Bill Smith* and *William Smith*, the reconciled Person reads *William Smith* and the fact that he went by *Bill* disappears from the headline name. The evidence still exists on the Observations, but the conclusion loses a real, frequently useful fact (what the person was actually called) and the researcher has to re-enter it by hand as a `nick` part.
- **Wanted:** Keep the fold (one Person, formal given name wins) but carry the folded short form forward as a **`nick` part** of the assembled name — *given: [William], nick: [Bill]* — instead of dropping it. Initials (`J` → `James`) and abbreviations (`Wm` → `William`) still vanish; only nickname-class folds surface (decided 2026-10-28, below).

## Decisions (Jake, 2026-10-28)

Verbatim: "Yeah obviously abbreviations would fold but nicknames would be re-tagged."

- **Nickname-class folds re-emerge.** A fold that value compare pairs through the nickname alias tables (`AliasKind == nickname`, `CauseAlias`; e.g. *Bill* → *William*, *Bob* → *Robert*) keeps folding for the purpose of choosing the formal given name, but the folded word is re-emitted as a `nick` part of the assembled name instead of disappearing.
- **Abbreviation and initial folds keep folding away** exactly as today: *Wm.* → *William* (`CauseAbbreviation`) and *W.* / *J.* → *William* / *James* (`CauseInitial`) leave no trace in the output name.
- **Discriminator.** `det.Parts[i].Cause` from `valuecompare.Compare` inside `nameModule.fold` already separates the three classes per paired word, so no new data is needed to tell them apart.

## How it works today (observed, not implemented)

- **Where the fold happens.** `core/autoreconcile/names.go` — `nameModule.fold(typ, from, into)`: a unit (one part type's words) folds into a fuller one when `valuecompare.Compare` says *into* contains or is equivalent to *from* and every paired word is the same, an initial (`CauseInitial`), or an alias (`CauseAlias` / `CauseAbbreviation`) that `rules.Names.Aliases.Expands(from, into, role)` allows for that part's role. The pipeline (`core/autoreconcile/pipeline.go`, `ReasonFolded`) then marks *Bill* as folded into *William*; `assemble` rebuilds the name only from **surviving** units, so the folded word is gone from the output.
- **Alias tables.** `core/valuecompare/aliases.go` — `AliasIndex` with `AliasKind` `abbreviation` | `nickname`, `FormalFirst` sets (head = formal name), and `AliasDirection{Formal, Nickname}` for pairs listed both ways; `Expands` is the one-way "folds toward" check. Seeds in `core/database/namealiases/` — `nicknames_seed.go` (`nicknameSets`, carltonnorthern/nicknames CSV), `nickname_directions.go` (`nicknameDirections`, e.g. `{william, bill}`, `{robert, bob}`), abbreviations in `registry.go`. Stored per catalog in `name_alias_tables` / `name_alias_members` / `name_alias_roles` (`000049.sql`); roles allowed for the product tables are `given`, `nick`, `untyped`. The reconciler reads the product seed via a cache (`autoreconciler.CacheVersion`). So the data to tell "nickname" from "abbreviation" from "initial" is already in `det.Parts[i].Cause` and the table's `Kind` at fold time.
- **Does a nickname slot exist? Yes — as a name part type, not a Property.** `nick` is a structured-name part type (`core/namevalue/namevalue.go` `PartTypeNick`, registry `nameValue.part.type.nick`, GEDCOM `NICK` in `docs/seeded-vocabulary.md` §4.1) with a place in both Western format styles (`core/database/nameformats/registry.go`: natural order `prefix, given, nick, surname_prefix, surname, suffix`; sorted order after `given`) and matching role `RoleNick`. Swift renders it through `NamePartType.nick` / `L10n.NameValue.partTypeNick`. There is **no** separate `nickname` Property in `subjectvocab` `seedProperties`, and none is needed for the ask: the output is the Person's single reconciled `name` NameValue, which can already carry `nick` parts.
- **Existing precedent in the reconciler.** `docs/conclusion-reconciliation.md` §7.2 "One name, never mixed": *nick Jake* + *given James* already assembles to `given: [James], nick: [Jake]` when a source typed the part as `nick`. The ask is to produce that same shape when the source typed *Bill* as `given` and the alias table, not the researcher, is what knows it is a nickname. `assemble` (`names.go` ~L174) already handles multi-type ordering, so the change is in what the fold hands forward, not in assembly.
- **Display / downstream.** `core/database/conclusionheaders` composes the Person title from the reconciled name via `nameformats.Format`, so a `nick` part would show in natural order ("William Bill Smith" unless the format quotes nicknames — check how `Format` renders `nick` today). `core/matchregistry/value.go` maps `nick` → `RoleNick` for matching, so an emitted nick would also start feeding similarity. Persons list sort (`conclusionheaders/order.go`) uses the sorted style, which places `nick` after `given`.

## Open questions

- ~~**Which folds re-emerge?**~~ Resolved 2026-10-28 (see Decisions): nickname-class only (`CauseAlias` via a `nickname` table) re-emerges as `nick`; abbreviations (`CauseAbbreviation`) and initials (`CauseInitial`) keep folding away. `det.Parts[i].Cause` is the discriminator.
- **Provenance of the emitted part.** Today every part of the assembled name comes from a recorded `namevalue.Part` of some member (`assemble` keeps `raw`). An emitted nick would be the folded member's `given` part re-typed as `nick` — a part the source never recorded as a nickname. Does that need marking (a reason like `ReasonFolded` but on the surviving side, or a distinct `ReasonRetyped`), and how does the reconciliation reasoning view explain it?
- **Cardinality / duplicates.** A Person with *Bill*, *Billy*, and *William* across sources: both nicks, or only the most-supported? `assemble` already dedupes identical words per type, so distinct nicks would all survive unless capped.
- **Interaction with a researcher-typed `nick`.** If one source already recorded `nick: Bill` and another `given: Bill`, the fold path and the existing nick path must agree on one `nick: [Bill]`, not two.
- **Format rendering.** Whether `nameformats.Format` should quote or parenthesise `nick` ("William 'Bill' Smith") is a display question that becomes visible the moment nicks appear automatically.
- **Pinned / concluded names.** A researcher-pinned name takes rank 1; does the emitted nick still attach to it, or only to auto-reconciled results?
- **Cache.** Any change here bumps `autoreconciler.CacheVersion` (the seed comment already says so for direction edits).
